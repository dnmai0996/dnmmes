## 새 계정 서버 단위·모의 시험
- 관리자 검증, 비관리자 차단, 이메일/버전/동의/요청형식 검사
- Origin·JSON·요청크기, 서버키 타입·프로젝트 일치 검증
- 초기 Auth 암호는 1111이 아닌 무작위 값으로 설정, 응답에 비밀번호 노출 없음
- 신규 생성과 기존 사용자 초기화 구분, idempotent 완료 결과 재사용
- Auth 오류 시 false success 방지, 개인암호 설정 실패 시 업무허용 금지
- 초기번호 scrypt 검증, 알 수 없는 계정/중지 계정/틀린번호 차단
- 임시로그인은 업무용 Auth 토큰 대신 1회 설정티켓만 반환
- 초기 설정 권한 재사용 차단(모의상태), 짧은 비밀번호 차단
- 관리자 재인증, 본인 현재암호 확인, current_password 전달
- 프런트엔드에 service_role/secret key를 전달하지 않는 구조 및 SQL grant 정적검사

## Chromium 실습 흐름
1440px 관리자 목록, 계정등록 체크, 본인메일·소유확인, 초기화 사유·관리자암호,
사용중지, 본인암호 변경 후 로그아웃, 일반사용자 관리자메뉴 미노출 확인.
320/360/390px 최초 비밀번호 화면: 가로넘침 없음, 업무메뉴 없음, Auth 세션 미저장,
비밀번호 확인 불일치 안내 및 성공 후 새 개인로그인 안내 확인.
360px 관리자 목록은 표 영역 내부 가로스크롤 사용; 페이지 전체 가로넘침 없음.

## 수행하지 않은 검사(중요)
- 실제 PostgreSQL의 10_upgrade_v4_3.sql 실행 및 트랜잭션·RLS 동작
- 실제 Supabase Auth 관리자 API, Secret key 라우팅, 정책·세션 폐기/갱신 검증
- 실제 Netlify Functions 배포·환경변수·HTTPS Origin·context.ip·시간제한
- 실제 임직원 계정 등록, 실제 업무자료 조회·수정·보관, 모바일 실제기기
- 이 작성환경에서는 DB 실행 바이너리·외부 패키지 다운로드를 사용할 수 없어 DB 실행 검사를 수행하지 못함

따라서 ‘165개 통과’는 실제 운영 DB 검수 통과를 의미하지 않습니다.
`.github/workflows/verify.yml`에 임시 PostgreSQL17에서 기존 이행과 새 계정보안 회귀시험을 제공했습니다.
GitHub Actions 통과 후 별도 시험 Supabase에서도 UPGRADE_v4_3_KO.txt의 11절 검수필수입니다.
검수 실패 시 운영계정 발급을 시작하지 마십시오. 오류를 기록하고 보완하며 DB/계정을 삭제하지 않습니다.
