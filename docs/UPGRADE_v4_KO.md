# 디엔엠 Cloud MES v4.0 업그레이드 안내

## 0. 적용 대상과 주의
이 파일은 DNM_Cloud_Admin_v3.0 + DNM_Login_Patch_3.0.1 운영 앱의 확장본입니다.
디엔엠 연차관리(dnmannual), SB선보 복지챗봇, 구 MySQL MES 저장소에 덮어쓰지 않습니다.
현재 v3 MES가 연결된 GitHub 저장소·Netlify 프로젝트·Supabase 프로젝트를 유지하십시오.
이 ZIP 자체를 단순 Netlify Drop으로 별도 새 사이트에 만들지 않는 것이 안전합니다.

중요: 제공된 RC2 ZIP은 전체 프로그램이 아닌 패치였습니다. 그 안에서 확인한 기능을 이식하고 나머지 서버 업무흐름은 새로 구현했습니다. 상세 범위는 FEATURE_MATRIX.md를 참조하십시오.

## 1. 기존 자료와 설정 백업
1) 현재 GitHub 저장소의 Commit을 기록하거나 `v3-before-v4` 태그를 만듭니다.
2) 현재 public/config.js를 PC의 별도 안전한 위치에 복사합니다.
3) Supabase에서 현재 DB의 복구 가능한 백업을 확보합니다. 앱의 JSON 내보내기만으로 Auth 로그인 계정·비밀번호까지 복구되지는 않습니다.
4) 기존 사용자·품목·거래처·메모의 건수를 기록합니다.
5) 테스트 중 실제 입력을 잠시 중단할 시간을 담당자와 정합니다.

## 2. GitHub에서 시험 브랜치로 파일 적용
1) 기존 v3 MES 저장소에서 `upgrade-v4` 브랜치를 만듭니다.
2) ZIP 압축을 풉니다. 그 안의 public, database, docs, tools, tests, .github, package.json, netlify.toml을 저장소 최상위의 같은 경로에 복사합니다.
3) 기존 public/config.js는 그대로 둡니다. ZIP에는 config.js를 의도적으로 넣지 않았습니다.
4) public/public처럼 한 단계 더 들어간 폴더가 없는지 확인합니다.
5) Commit/Push합니다. GitHub Desktop 로그인은 해당 MES 저장소 쓰기 권한이 있는 계정을 사용합니다.
6) GitHub의 Actions에서 ‘DNM v4.0 verification’ 결과를 확인합니다. 실패하면 운영 DB에 SQL을 적용하거나 main으로 합치지 말고 실패 로그를 먼저 검토합니다.

※ 시험 브랜치도 운영 Supabase 설정을 그대로 가지고 있다면 실제 데이터를 변경할 수 있습니다. Preview는 별도 시험 Supabase 프로젝트를 사용하거나 가상데이터 테스트로 제한하십시오.
※ 이 문서 작성환경에서는 GitHub Actions/PostgreSQL 실행을 실제 수행하지 못했습니다. 자동검증 파일은 제공했지만 통과했다고 주장하지 않습니다.

## 3. Supabase DB 확장
기존 프로젝트에 접속 → SQL Editor → 새 쿼리
→ `database/04_upgrade_v4.sql` 전체 복사 → 붙여넣기 → Run

- 04는 기존 dnm_portal_* 및 Auth 계정을 보존하고 dnm_v4_* 테이블과 업무 함수를 추가합니다.
- 기존 설치에서는 01_schema.sql과 02_first_admin.sql을 다시 실행할 필요가 없습니다.
- RC2의 MySQL grants.rc2.sql, fix-import-grants.sql은 Supabase에서 실행하지 않습니다.
- 오류 발생 시 오류 전체를 기록하고 중단합니다. 데이터 삭제·테이블 초기화로 해결하지 않습니다.
- 시험 프로젝트에서 검증한 다음 운영 프로젝트에 같은 04 파일을 적용하십시오.
- 이후 `database/05_verify_v4.sql`을 실행합니다. 이 파일은 조회 점검용이며 자료를 수정하지 않습니다.

새 프로젝트를 처음 만드는 경우에만:
01_schema.sql → Supabase Authentication/Users에서 개인별 계정 생성 →
02_first_admin.sql에 본인 관리자 이메일 입력/실행 → 04_upgrade_v4.sql → 05_verify_v4.sql
public/config.example.js를 config.js로 복사하고 Project URL/Publishable key를 입력합니다.
기본 admin/1111 같은 공용 비밀번호는 이번 v4에 새로 생성하지 않습니다.

## 4. 기존 운영 사이트 배포
시험 결과를 승인한 후 upgrade-v4를 main에 합칩니다.
기존 Netlify 프로젝트의 Deploys에서 새 배포가 Published인지 확인합니다.
배포 설정: Publish directory = public / Build command = 빈칸
로그인 화면/좌측 하단 버전이 4.0.0인지 확인합니다.
일반 재배포로 반영되면 추가 캐시 삭제 배포를 반복하지 않습니다.
실제 주소에서 Ctrl+F5로 새로고침하고 이전 이메일·비밀번호로 로그인합니다.

## 5. 권한 지정
관리자 로그인 → 사용자 관리: 기존 계정 활성상태 확인
→ 업무권한·전결: 생산/구매/품질/기준정보/결재/작업 권한 부여

- 관리자: 업무 관리 권한 보유. 그러나 구매결재는 결재선의 현재 담당자여야 하며 자기 결재는 불가합니다.
- 담당자(member): 기본 작업 입력 권한. 추가 업무는 관리자가 부여합니다.
- 조회자(viewer): 조회 전용. 권한 체크만으로 쓰기 권한을 우회할 수 없습니다.
- 전결: 결재 권한과 별도로 한도와 만료일을 관리자가 입력합니다. 후속 ‘필수 결재’는 전결로 생략할 수 없습니다.
- 직원명과 Supabase 이메일 계정은 서로 다릅니다. 작업자 메뉴에서 실제 계정과 연결해야 합니다.

## 6. 기준정보와 원본 자료 가져오기
‘자료 가져오기’ 버튼 → 원본 XLSX 또는 별도 .dnm.json 선택 → 미리보기
→ 고객명(수주), 검토사유 입력 → 원본 대조 체크 → 등록

권장 순서:
1) 품목 / 거래처 / 공구·공급업체
2) 설비 / 계측기 / 작업자
3) 설비별 관리자와 작업자 로그인 연결 및 사용 활성화
4) 설비·작업자 연결: 가능공정명 입력
5) 공정 템플릿: 공정순서와 종류(가공/소재/검사/외주/포장) 확인
6) 고객수주: 고객명·PO 행번호·납기·품번 확인
7) Routing 작성 → 각 가공공정 배정 → 배포

수주 Excel의 ‘협력업체명’은 디엔엠일 수 있으므로 고객명으로 자동 사용하지 않습니다.
PO 행번호가 원본에 없으면 공란을 유지합니다. 계약품목번호나 PR순번을 대신 입력하지 않습니다.
원본 A~CD의 82열과 C/AO의 ‘상태’ 열은 각각 보존합니다.
기준정보 가져오기는 400행 이하 단위로 나누어 처리합니다. 중간 실패 시 이미 완료된 건수는 보존하며 다시 조회 후 재시도합니다.

중복 품번·템플릿, ‘다수 보유’ 등 개별 관리번호 미제공 항목은 차단됩니다. 기준정보는 ‘차단 오류 행 제외’를 명시적으로 체크한 경우에만 정상 행을 먼저 등록할 수 있습니다. 수주는 오류가 있으면 원본 수정 후 다시 등록합니다.
단가·단위가 없는 공구 원본은 구매요청 시 담당자가 확인하여 입력합니다.
원본을 자동 정답으로 확정하지 않습니다. 실설비 대수/개별 가용 여부와 원본 행수는 다릅니다.

## 7. 실제 운영 전 반드시 확인할 시나리오
A. 기존 v3 이메일 로그인, 사용자/품목/거래처/메모 보존
B. 관리자·생산담당자·작업자·조회자 각각의 조회/등록 제한
C. 수주 → Routing → 배정 → 배포 → 시작 → 완료 → 수량 확인 → 최종검사 → 출하 → 수주 마감
D. 구매요청 → 1차 결재 → 최종승인 또는 유효 전결 → 발주 → 부분입고 → 반품 → 재입고 → 증빙대사 → 지급기록
E. 중복 클릭/통신 끊김 후 재확인 시 중복 자료가 생기지 않는지 확인
F. 미승인 발주, 과다 입고, 선행공정 미완료 시작, 과다 출하, 자기결재 차단
G. PC·휴대폰·TV의 같은 데이터 조회와 15초 갱신/마지막 갱신시각
H. 업무 JSON 백업과 Supabase 복구수단 각각 확보

## 8. 실패 시 대응
- 로그인 오류: 로그인 아래 Supabase 연결 진단 → 기존 config.js가 유지됐는지 확인
- dnm_v4_context/command를 찾지 못함: 04 SQL 적용 여부/오류/같은 프로젝트 연결 확인
- 사용권한 없음: 계정 active/role 및 업무권한 확인
- 중복/원본 오류: 미리보기의 차단 오류 행을 원본과 대조. 임의 번호로 우회 금지
- 저장 응답 없음: 팝업의 ‘같은 요청 다시 확인’ 또는 목록 조회. 새 요청을 무조건 반복하지 않음
- Routing 배포 실패: 관리자-설비-작업자-가능공정 연결 및 로그인계정 활성 상태 확인
- 기존 화면으로 되돌리기: 기존 Git Commit으로 웹앱만 롤백. v4 테이블을 임의 삭제하지 않음

## 9. 기능상 제한
PDF 자동 판독/OCR, XLSM 매크로 실행, 원본 성적서 서식 100% 재현, 전자서명, 사내 Ollama 연결, 완전한 재공품/창고이동 원장은 포함하지 않습니다.
품질문서는 문서번호·구분·참조경로·검토이력을 관리합니다. 바이너리 파일 저장소 업로드 기능과 다릅니다.
음성은 지원 브라우저에서 사용자 동의 후 이용하며, 외부 음성서비스를 사용할 수 있습니다. 민감자료는 음성 사용 승인 전 수기로 입력하십시오.
