# v4.0 운영 전 검토 조건

1. 실제 Supabase/PostgreSQL 실행 검증은 작성환경에서 수행하지 못했습니다. GitHub Actions의 임시 Postgres 테스트 및 별도 Supabase 실사용 검수가 선행되어야 합니다. 47개 로컬 테스트 중 SQL 관련 5개는 코드 정적 검사입니다.
2. 현재 자료는 RC2 전체 소스가 아닙니다. 원본과 모든 화면/규칙의 동일성을 보장하지 않습니다.
3. 하나의 Supabase 프로젝트를 하나의 회사 데이터영역으로 사용합니다. 여러 회사 테넌트 분리 시스템이 아닙니다.
4. v4 자료는 업무 건별 개별 레코드와 JSONB 세부항목을 사용합니다. 전체 DB를 하나의 공유 JSON으로 덮어쓰는 방식은 아닙니다. 업무 트랜잭션은 인증/권한을 검사하는 DB 함수에서 처리합니다.
5. 초기 동시변경 제어는 업무 명령에 트랜잭션 advisory lock을 적용합니다. 대용량·다수동시사용 성능은 측정하지 않았습니다. 약20명 운영 전 부하 측정이 필요합니다.
6. 일반 조회는 종류별 최대20,000건을 안전한 페이지로 읽습니다. 장기 대용량 운영은 서버집계·기간필터 고도화가 필요합니다. 자동갱신은 15초 폴링이며 Realtime/WebSocket이라고 표기하지 않습니다.
7. 기존 v3 관리자/member/viewer 역할을 유지합니다. member는 기본 작업권한만 있으며 필요한 업무권한은 별도 지정합니다. 운영 전 최소권한 계정으로 직접 차단 여부를 검증하십시오.
8. 구매결재는 자기결재 불가, 현재 순번만 결재, 전결은 금액한도·기한 확인, 후속 필수 결재 생략 불가가 기본정책입니다. 대표자 또는 관리자라는 이유만으로 전결 처리하지 않습니다.
9. 구매수량은 정수, 단가는 소수2자리까지, 부가세율은 입력에 따라 0 또는10%를 사용합니다. 계근·길이·소수수량 업무는 적용 전 추가 설계가 필요합니다. 원화 계산규칙과 세금처리는 회계담당자에게 확인하십시오.
10. 정산은 전체 합격입고 완료 + 승인금액/증빙금액 일치 후 진행하며, 지급은 증빙참조 기록일 뿐 실제 송금이 아닙니다. 정산 후 반품·차액 정정은 자동 처리하지 않습니다.
11. 제품별 Routing은 먼저 초안을 작성/수정하고 배포합니다. 실제 작업실적이 발생하면 기존 경로를 교체하지 못하게 보호합니다. 재작업·분할 LOT·부분이관과 병렬공정은 별도 설계가 필요합니다.
12. 가공공정은 선행공정 완료 후 시작합니다. 같은 작업자 또는 설비에 진행 중 작업이 있으면 중복 시작을 제한합니다. 다설비 동시운전이 실제로 필요한 경우 운영정책 검토 후 확장해야 합니다.
13. 작업시간은 Asia/Seoul 기준 정수 분 저장입니다. 현재 기본 제외시간은 09:30~09:40, 11:30~12:30, 14:30~14:40입니다. 최대 단일 입력72시간, 미래 시각 제한을 적용했습니다. 실근무·휴게와 다르면 domain.js와 SQL minutes 함수를 함께 수정·시험해야 합니다. 급여/법정근로시간 확정용 시스템은 아닙니다.
14. 수량 없이 완료하면 ‘수량확인대기’로 보존합니다. 최종확인 전에는 생산수량에 합산하지 않습니다. 최종 합격진척은 최종검사 합격수량/주문수량이며 중간공정 수량을 합산하지 않습니다.
15. 브라우저 SpeechRecognition은 PC/휴대폰/브라우저에 따라 지원이 다르고 외부 음성서비스를 사용할 수 있습니다. 오프라인 Ollama/STT는 연결하지 않았습니다. 숫자 추출은 보수적 규칙 방식이며 사용자가 확인하기 전 DB에 저장하지 않습니다.
16. 품질문서는 문서대장·참조경로·시스템 기록사본입니다. 원본 PDF/XLSM 자동 해석, 매크로 실행, 원본고객서식 100% 재현, 전자서명/공식 품질보증 발행은 아닙니다. PDF 자료는 원본을 사람이 대조합니다.
17. 제공한 원본 Excel 읽기는 값·시트·행 위치 중심입니다. 이미지/도형/병합스타일/계산식 재계산/매크로는 수행하지 않습니다. 수식은 저장된 캐시값만 사용하고 이상값은 차단합니다. 복잡한 도형 공정도는 자동 Routing 확정에 사용하지 않습니다.
18. Native XLSX 가져오기는 DecompressionStream(deflate-raw)/Worker가 있는 최신브라우저가 필요합니다. 회사 정책상 제한되면 제공된 로컬 Python 변환기를 사용해 .dnm.json을 생성한 후 가져오십시오. 브라우저 메모리가 작은 휴대폰보다는 관리자 PC 사용을 권장합니다.
19. 자료 가져오기에서 중복코드/개별번호 미제공 행은 등록을 차단합니다. 기준정보에 한해 사용자가 제외 옵션을 선택하면 정상행만 먼저 등록할 수 있습니다. 제외한 행은 원본에서 해결 후 다시 미리보기하십시오. 수주는 원본 오류 해결 전 전체 등록을 차단합니다. 단가·단위·고객명·PO 행번호 등 미제공값은 임의 추정하지 않습니다.
20. 직원 데이터는 사번·성명·부서·직책·입사일·Auth 연결 중심이며 민감한 주민등록번호 자동수집은 하지 않습니다. 신규 Auth 계정은 Supabase 관리자에서 생성합니다.
21. 업무 JSON 백업은 Auth 비밀번호, 실제 첨부파일, Supabase 시스템구성을 포함하지 않습니다. 관리자 별도 DB백업/복원훈련이 필요하며 자동복원/초기화 기능은 미포함입니다.
22. 초기 계정·비밀번호는 새로 생성하지 않습니다. 기존 계정을 유지하고 공유 비밀번호·약한 비밀번호는 관리자가 변경해야 합니다. MFA·SSO·비밀번호 분실메일 UI는 기존 v3와 동일하게 별도 기능이 없습니다.
23. 공개 GitHub/Netlify 파일에는 원본 고객자료·직원자료·비밀키를 넣지 마십시오. 브라우저에서 쓰는 publishable 키 자체는 데이터 보호장치가 아니며 실제 접근제어는 Auth·RLS·업무 함수가 담당합니다.
24. 테스트용 실제 고객·방산 정보를 Supabase 외부서비스에 저장하기 전 회사 정보보안 기준과 계약조건을 검토하십시오. 로컬 보관/기업승인 요구가 있으면 가상 데이터로만 사용하십시오.
