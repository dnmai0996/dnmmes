# v4.3 현재 제한 및 운영 전 검수

1. 제작환경에서는 Supabase·Netlify에 접속하거나 계정을 직접 생성하지 않았습니다. 실제 PostgreSQL SQL 실행과 Supabase Auth 관리자 API, RLS, 세션 폐기 동작은 미검증입니다.
2. 로컬 자동검사는 코드·모의 API·가상 Chromium 기준입니다. GitHub Actions와 별도 시험 Supabase의 실제 검수를 통과한 뒤 운영에 적용해야 합니다.
3. 신규 서버 환경변수 2개가 필요합니다. 공개키만으로 관리자 API를 호출할 수 없으며 관리키를 브라우저/GitHub에 넣으면 안 됩니다.
4. 1111은 30분 초기설정 전용, 설정티켓은 최대5분입니다. 사용자 편의를 위해 고정번호를 채택했으므로 이메일을 아는 사람이 먼저 변경할 위험은 남습니다. 당사자 확인·필요시 회사망 제한이 필요합니다.
5. 직원메일 자동추정·대량 무인계정 생성·메일인증 자동발송은 하지 않습니다. 초기 관리자 승인으로 메일 소유를 확인하는 구조입니다.
6. 기존 이메일의 일반계정 재사용·작업자 매핑은 지원하지만, 연결 이후 이메일 변경과 관리자 자신의 분실암호 복구는 별도 관리절차입니다.
7. 실제 작업자 재직확인, 설비·공정 배정, 개별 메뉴권한, Routing 배포는 별도 승인업무입니다. 계정 발급만으로 담당작업이 생기지 않습니다.
8. 초기화/비밀번호변경 시 이전 세션은 DB 접근규칙으로 차단하지만 이미 화면에 내려온 자료나 다운로드된 파일을 원격삭제하지 않습니다.
9. 업무 JSON 백업은 Auth/private 계정제어/Storage 바이너리의 완전한 복원본이 아닙니다. 프로젝트 전체 백업·복원 체계를 유지하십시오.
10. 기존 브라우저 음성 기능의 기기호환·외부 음성서버 전송 및 원본 품질양식 재현 등 v4.2.1의 제한은 그대로입니다.
11. public/config.js와 실제 기준정보 PRIVATE 파일은 패키지에 포함하지 않았습니다. 기존 자료를 보존합니다.
12. Netlify Functions 실패가 기존의 정상 개인 비밀번호 로그인 자체를 반드시 막는 구조는 아니지만, 신규등록·초기화·개인 비밀번호 변경 서버기능은 사용할 수 없습니다.
13. 현재 프로젝트는 단일 회사용입니다. 서비스키는 강한 관리권한을 가지므로 최소 관리자만 접근하고 유출 시 교체하십시오.

과거 버전의 설치 문서보다 UPGRADE_v4_3_KO.txt와 ACCOUNTS_SECURITY_v4_3.md를 우선 적용하십시오.
