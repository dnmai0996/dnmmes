DNM Cloud MES v4.1 — 수주·제품 Routing·작업일보 통합 수정본
작성 기준: 2026-10-28 / 기존 v4.0~4.0.2 운영 앱 대상

[가장 중요한 내용]
- GitHub → Netlify → Supabase 방식 유지. 사내 MySQL/Ollama 설치 변경 없음.
- 로그인 fetch constructor 수정(v4.0.2)을 포함함.
- 이번에는 화면만 교체하면 안 됨. 기존 v4.0 DB에 database/06_upgrade_v4_1.sql 확장 적용 필요.
- 기존 public/config.js를 반드시 그대로 보존. 이 ZIP에는 config.js를 의도적으로 넣지 않음.
- 회사 실데이터, 원본 Excel/PDF, 사용자 비밀번호, Secret key는 ZIP에 포함하지 않음.
- 실제 Supabase/휴대폰/마이크 현장 검수는 미실시. GitHub 자동검증 및 시험 프로젝트 검수 후 운영 적용.

1. 작업 전 백업
(1) 기존 MES GitHub 저장소의 현재 Commit 번호를 기록하고 전체 코드를 백업.
(2) public/config.js를 별도 안전한 폴더에 복사.
(3) 기존 Supabase DB의 복구 가능한 백업 확보. 앱의 업무 JSON 내보내기는 Auth 계정·비밀번호와 외부 첨부파일까지 포함한 전체 복구본이 아님.
(4) 운영자료의 입력을 일시 중단할 시간을 담당자와 협의.
※ 디엔엠 연차관리(dnmannual), SB선보 챗봇, 구 MySQL 프로젝트에 적용하지 말 것.

2. 먼저 시험 브랜치에서 파일 적용
(1) GitHub Desktop에서 현재 DNM MES 저장소 선택 → Repository → Show in Explorer.
(2) 시험용 upgrade-v4-1 브랜치 생성.
(3) ZIP의 public, database, docs, tests, tools, .github, package.json, netlify.toml 등을 같은 위치에 덮어쓰기.
(4) 기존 public/config.js는 삭제하지 않고 유지. public/public 중첩 폴더 생성 금지.
(5) Commit → Push origin.
(6) GitHub 웹사이트 Actions → DNM v4.1 verification 결과 확인.
※ 이 CI는 임시 PostgreSQL 시험용이며 회사 Supabase 접속정보가 필요하지 않음. 실패 시 main 반영·운영 DB 적용 중단.
※ Preview도 운영 config.js를 사용하면 운영 DB에 저장함. 별도 시험 Supabase를 사용하거나 비저장 화면 검증만 진행.

3. 기존 Supabase에 확장 SQL 적용
(1) 시험 프로젝트에서 먼저 검수. 운영 적용 시에는 현재 DNM MES가 쓰는 동일 Supabase 프로젝트 선택.
(2) SQL Editor → 새 쿼리.
(3) database/06_upgrade_v4_1.sql을 메모장으로 열어 전체 복사 후 붙여넣기.
(4) Run 실행. 오류가 나면 사용자/테이블 삭제나 초기화 SQL 실행 금지. 오류 전문 확인 후 조치.
(5) database/07_verify_v4_1.sql로 설치 함수·RLS 등의 조회 확인.
- v4.0 DB가 없는 신규 프로젝트에서만 기존 초기설정 안내에 따라 01, 04를 선행. 기존 운영자는 01·02 재실행 불필요.
- 06 적용 후 04를 재실행하면 업무함수가 옛 버전으로 돌아갈 수 있으므로 금지.
- 06은 계정/수주/실적 테이블을 삭제하지 않음. 완료조건을 충족한 기존 배포 Routing은 종료로 재판정할 수 있으며, 원 작업일보는 보존.
- 제품·거래처 직접 수정은 관리자 또는 master 업무권한으로 제한. 기존 담당자는 필요시 업무권한·전결에서 master 권한 확인.

4. 운영 Netlify 배포
(1) 시험 검수 승인 후 main에 반영하고 Push origin.
(2) 기존 Netlify 프로젝트 Deploys에서 새 배포 Published 확인.
(3) Publish directory는 public 유지, 별도 빌드명령 불필요.
(4) 브라우저에서 Ctrl+F5 → 화면 버전4.1.0 확인 → 기존 계정으로 로그인.
(5) 백업·운영점검에서 서버 버전4.1.0 확인.
- Netlify 사이트를 삭제하거나 새 프로젝트를 만들지 않음.
- 앱4.1/DB4.0이면 확장 SQL 안내를 표시하고 새 업무 작성을 차단함.
- DB 변경 후 옛 브라우저 탭은 모두 새로고침. rollback은 프런트만 되돌려 무조건 해결되는 작업이 아니므로 백업/변경관리 필요.

5. 초기 기준정보 확인 순서
① 사용자 관리: 직원 계정 활성화 및 역할 확인.
② 업무권한·전결: master / production / work 등 필요한 권한 지정.
③ 기준정보 → 작업자: 사번·성명·부서·직책·입사일, 활성 여부와 로그인 계정 연결.
④ 설비: 활성 여부와 담당 생산관리자 설정.
⑤ 설비·작업자 연결: 해당 설비·작업자·가능공정(공정명 정확히 일치) 등록.
⑥ 공정: 공정코드·명칭·종류·검사코드·기본 작업내용 등록.
⑦ 제품 / 제품 Routing 템플릿: 고객 자재코드(품번), 공정순서·설비·작업자 기본배정 검토.
⑧ 자재·매출처·매입처·계측기 기준정보 확인.
계정과 작업자 연결이 없거나 Routing이 미배포이면 작업자의 나의 작업 목록이 비어 있음.

6. 고객수주 Excel 업로드
고객 수주 → Excel 업로드 → 수주자료 XLSX 선택 → 12개 항목 미리보기 → 고객명·검토사유·원본대조 확인 → 등록.
12개 항목: PO 번호 / 자재코드 / 자재명 / 등급코드 / 발주수량 / 입고수량 / 발주단가 / 발주금액 / 발주일자 / 납기일자 / 생산오더 / Project내역.
- 실제 첨부 파일은 헤더+수주10행, A~CD82열로 읽기 검증.
- 원본82열은 계속 보존. C열 상태와 AO열 상태를 합치지 않음.
- 원본 C열 신규와 신규 제품 여부는 별개. 자재코드와 검토완료 템플릿 일치 여부로 표시.
- 기존 수주에 새 필드가 비어 있으면 해당 원본을 다시 업로드하고 기존 건 업데이트를 명시적으로 선택·검토. 이미 배포된 수주의 품번·지시수량 변경은 제한.
- 입고수량은 고객 수주자료 원본값이며 사내 자재입고/완료수량으로 대체하지 않음.
- 발주단가×수량으로 발주금액을 강제 재계산하지 않음. 원본 값 보존.
- 누락 금액·수량은 확인되지 않은 값으로 유지하며 임의 0 대입하지 않음.
- XLSM은 저장된 값만 읽고 매크로/수식 실행 안 함.

7. 신규 제품과 양산 매칭
신규 품번: 고객수주 → 제품 Routing 등록 또는 기준정보 → 제품 Routing 템플릿 → 공정 등록 → 검토완료 저장.
양산 품번: 등록된 동일 품번의 검토완료 템플릿 매칭 → Routing 작성 → 주문수량·납기·LOT·설비·작업자 확인.
- 유사한 품명으로 다른 제품을 자동 선택하지 않음.
- 템플릿 변경은 이미 배포된 Routing에 자동 반영하지 않음.
- 가져온 미검토 템플릿은 원본 대조 후 사용. 한 주문당 현재 배포 경로를 유지하고 실적이 있으면 새 경로로 임의 교체 불가.

8. Routing 작성·배포·출력
고객수주 → Routing 작성 → 담당관리자·LOT·문서정보 → 공정 추가/제외/순서변경 → 공정별 설비·작업자 → 초안 저장 → Routing·작업지시 → 공정·배정 → 배포 확정.
- 미배정 초안은 저장 가능하나 모든 가공 공정의 설비·작업자·계정·가능공정 연결 검증 전 배포 불가.
- Routing 메뉴: 진행 / 종료 / 전체. 정렬은 품번 → 납기일 → Routing번호.
- 조회 검색은 입력 중 필터링 또는 검색버튼 사용. 상태조건과 함께 적용.
- 출력은 첨부 RoutingSheet F7031-03의 항목과 표 구조를 A4로 재현. 인쇄 배율100%, 브라우저 머리말/꼬리말 해제 권장.
- 공정10개 초과는 이어지는 장으로 출력. 긴 작업내용은 인쇄 미리보기에서 페이지 분할을 확인.
- 기존 서명·도장 이미지 복제 없음. 입력 성명은 서명을 대신하지 않음.

9. 터치 작업입력
작업자 로그인 → 터치 작업입력(기본 첫 화면) → 본인 작업 → 작업 시작 → 작업 종료 또는 공정 완료.
- 작업 종료: 일부 수량 처리 후 다시 시작 가능. 수량 미확정이면 확인대기로 보관.
- 공정 완료: 누적 총처리량이 지시수량과 같아야 함. 부족한 경우 종료로 등록.
- 큰 숫자키/스마트폰 숫자 키보드/직접 문자 입력 지원.
- 수기 작업일보는 시작·종료시각·수량·등록사유 입력.
- 한 작업자 또는 같은 설비의 동시 진행 작업은 차단. 복수설비 동시운영은 별도 승인·설계가 필요한 범위.
- 공수는 정수 분. 휴게09:30~09:40, 점심11:30~12:30, 휴게14:30~14:40 제외 기준을 유지.
- 모든 공정 완료 및 미확정/진행 실적 없음 → Routing 자동 종료.
- 공정 완료/종료는 품질합격·고객출하·수주마감과는 별도 단계.

10. 음성 작업입력
음성 작업입력 메뉴 → 배정작업 선택 → 회사 음성처리 정책 확인 → 음성 입력 → 인식원문 확인/수정 → 인식 내용 확인 → 동작·총수량·불량수량 확인 → 저장.
예: 작업 시작 / 작업 종료 총수량 4개 불량 0개 / 공정 완료 총수량 6개 불량 0개.
- 음성은 자동 저장하지 않음. 숫자가 없거나 애매하면 사용자에게 입력/수정을 요구.
- 이 버전은 브라우저 SpeechRecognition. Ollama·로컬 whisper 연결은 포함하지 않음.
- Chrome 등에서는 음성이 외부 서비스로 전송될 수 있으며, 브라우저·네트워크·마이크 권한에 따라 동작이 다름.
- 방산·개인정보 등 회사 정책상 외부 처리 금지 자료는 음성 기능을 쓰지 않고 터치입력 사용.
- 해당 작업을 먼저 선택하므로 사람 이름/제품번호를 음성으로 자동 추정하지 않음.

11. 현장 TV·작업일보
작업진척 대시보드 → 고객주문/Routing별·설비별·작업자별 → TV 전체화면.
- 15초 주기 조회, 마지막 조회시각과 연결상태 표시.
- 공정별 처리수량/지시수량 표시. 중간공정 처리량을 납품수량으로 합산하지 않음.
- 진척률은 공정별 처리비율의 평균으로, 작업시간 가중치/OEE/실제 센서가동률이 아님.
작업일보 → 작업일·작업자·문자검색 → 인쇄/CSV.

12. 검증 범위와 한계
실행: JavaScript 문법, 단위/정적 회귀 테스트, Chromium 모의 API 화면·입력·인쇄·반응형 시험, 실제 수주XLSX 읽기.
미실행: 실제 Supabase/PostgreSQL의 SQL 실행, 사용자 운영계정 인증, 실제 Netlify 배포, 실물 휴대폰/터치장비 마이크,20명 동시접속.
GitHub Actions에 임시 PostgreSQL 통합시험을 제공하지만 본 환경에서 CI 실행 성공을 확인한 것은 아님.
따라서 시험 프로젝트에서 업무단계와 권한·자료보존을 확인하고 정식 운영에 적용.
오류 발생 시 06 SQL 오류 전문 또는 화면 오류를 기록. 계정·DB 삭제/초기화 금지.
