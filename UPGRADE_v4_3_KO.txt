DNM Cloud MES v4.3.0 — 프로그램 내 작업자 계정 등록·초기화 안내
기준: DNM Cloud MES v4.2.1 / GitHub → Netlify → Supabase 유지

[먼저 알아둘 내용]
직원이 Supabase 홈페이지에 가입하거나 들어갈 필요는 없습니다.
관리자가 DNM 프로그램에 로그인한 후 작업자의 ‘로그인 사용자’를 체크하고 본인 이메일로 등록합니다.
직원은 같은 DNM 주소에서 본인 이메일 / 초기번호 1111로 접속한 후, 반드시 본인 비밀번호를 먼저 설정합니다.
인증정보와 업무자료는 계속 기존 Supabase에 보관합니다. Supabase를 다른 DB로 바꾸는 프로그램이 아닙니다.

1111은 공용 초기번호이므로 30분 동안 비밀번호 설정에만 사용할 수 있습니다.
1111 자체를 Supabase Auth의 실제 비밀번호로 저장하거나 최소 비밀번호 길이를 낮추지 않습니다.
초기번호 접속 후 설정화면은 최대 5분, 원래 30분 만료시각 이내에서 유효합니다.
설정 전에는 작업지시·구매·품질 등 업무자료 접근을 차단하도록 DB 권한 규칙을 추가했습니다.
본인 비밀번호 설정 이후 1111은 사용할 수 없습니다. 기존 계정의 개인 비밀번호를 사용하려면 평소처럼 로그인합니다.
고정번호와 직원 이메일을 아는 사람이 먼저 비밀번호를 설정할 위험은 남습니다.
관리자가 당사자의 이메일 소유와 재직을 확인하고, 직원이 접속할 때에만 초기화해 주십시오.
공개 메신저에 전체 직원의 이메일/초기번호 명단을 배포하지 마십시오.

[1. 이번 파일이 필요한 위치]
- DNM_Cloud_MES_v4_3.zip: 전체 소스 보관 또는 기존 MES 저장소에 병합하는 용도
- DNM_MES_v4_3_User_Login_Patch.zip: 현재 v4.2.1 저장소에 덮어쓸 변경 파일(권장)
- DNM_v4_3_Supabase_Upgrade.sql: 동일 내용이 database/10_upgrade_v4_3.sql에 포함
두 프로그램 ZIP을 모두 적용할 필요는 없습니다.
연차관리 dnmannual, SB선보 복지챗봇, 사내 MySQL 프로그램 저장소에 적용하지 마십시오.
기존 DNM MES GitHub 저장소, Netlify 사이트, Supabase 프로젝트를 그대로 사용합니다.
이번에는 화면파일뿐 아니라 netlify/functions/와 server/의 계정처리 서버파일이 추가됩니다.
public 폴더만 올리면 계정 생성·초기화가 작동하지 않습니다.
기존 public/config.js는 반드시 보존합니다. ZIP에는 config.js와 실제 키를 넣지 않았습니다.
기준정보 PRIVATE 자료는 다시 등록할 필요가 없습니다.

[2. 운영 적용 전 백업·시험]
1) 현재 GitHub 커밋을 기록하고 public/config.js를 별도 안전한 위치에 보관합니다.
2) Supabase의 복구 가능한 DB/Auth 백업 수단을 확보합니다.
   앱 업무자료 JSON 백업은 Auth 비밀번호·private 계정제어·실제 첨부파일의 전체 복구본이 아닙니다.
3) 현재 v4.2.1 저장소에서 upgrade-v4-3 시험 브랜치를 만듭니다.
4) 패치의 파일·폴더 전체를 같은 위치에 병합합니다. public 폴더를 삭제하지 않습니다.
5) GitHub Actions ‘DNM v4.3 verification’이 통과하는지 확인합니다.
6) 별도 시험 Supabase와 시험 계정으로 먼저 검수합니다.
   Preview에서도 운영 URL/키를 사용하면 운영 DB를 변경합니다. 시험용 URL·공개키·서버키를 한 프로젝트로 맞추십시오.
7) 실제 검수 완료 후 담당자가 승인한 시간에 운영 프로젝트에 적용합니다.

[3. Supabase 확장 SQL — 설치 담당자가 한 번 수행]
전제: v4.2 DB 확장인 08_upgrade_v4_2.sql까지 적용된 프로젝트입니다.

1) 기존 Supabase 프로젝트를 엽니다.
2) SQL Editor → 새 쿼리를 엽니다.
3) database/10_upgrade_v4_3.sql 전체를 복사하여 붙여넣습니다.
4) Run을 누르고 성공 여부를 확인합니다.
5) database/11_verify_v4_3.sql을 실행하여 조회 점검합니다.
   anon_must_be_false = false
   user_must_be_false = false
   server_must_be_true = true
6) 오류가 나면 적용을 중단하고 오류를 기록합니다. 테이블 삭제·프로젝트 초기화로 해결하지 않습니다.

10은 직원·수주·Routing·작업일보를 삭제하지 않고 계정제어 테이블·업무 접근차단 규칙을 추가합니다.
기존 01/02/04/06/08 SQL을 다시 실행하지 마십시오. 이전 함수로 되돌아가 새 보안규칙과 충돌할 수 있습니다.
10을 적용했지만 새 화면이 아직 배포되지 않았다면 그 사이 직원 초기화를 하지 마십시오.
11은 상태 확인용입니다. 계정 암호·초기번호 해시·설정권한값을 조회하지 않습니다.
tests/sql의 파일은 GitHub의 버려지는 시험 DB 전용입니다. 운영 Supabase에 실행하지 마십시오.

[4. Netlify 환경변수 — 설치 담당자가 한 번 수행]
계정 생성·초기화는 Supabase 관리자 API를 사용하므로 공개키만으로 처리할 수 없습니다.
관리용 비밀키는 Netlify Functions에만 보관해야 합니다.
기존 public/config.js의 Publishable key는 계속 그대로 사용합니다.

Netlify → 기존 DNM MES 프로젝트 → Project configuration → Environment variables
→ Add a variable → Add a single variable
아래 두 항목을 하나씩 입력하고 저장합니다.

(첫 번째)
Key: DNM_SUPABASE_URL
Value: 현재 public/config.js의 SUPABASE_URL과 같은 https://프로젝트번호.supabase.co
끝의 /는 있어도 정리합니다. /rest/v1 같은 경로를 붙이지 않습니다.
Secret: 선택하지 않아도 됨
Scopes: Functions를 포함. 무료 화면에서 All scopes만 가능하면 그대로 사용
Values: Production에 운영 값을 지정. Preview에는 별도 시험 프로젝트 값을 지정하거나 비워 둠

(두 번째)
Key: DNM_SUPABASE_SECRET_KEY
Value: 같은 Supabase 프로젝트의 Secret key(sb_secret_로 시작하는 전체 값)
Secret: Contains secret values 체크
Scopes: Functions를 포함. 선택 기능이 없으면 All scopes
Values: 운영 배포 Production에 적용. 시험 Preview는 별도 시험 프로젝트 키만 사용

키 위치: Supabase → Project Settings → API Keys → Publishable and secret API keys
→ 아래쪽 Secret keys에서 복사
새 Secret key가 없으면 해당 프로젝트에서 발급합니다.
이전 방식의 service_role JWT도 서버키로 지원합니다. anon/Publishable key는 서버 관리자용으로 쓸 수 없습니다.
이번 ‘Secret key’는 이전 config.js용 ‘Publishable key’와 다릅니다.
Secret key를 config.js, GitHub, 엑셀, 채팅, 화면 캡처에 넣지 마십시오.
브라우저가 받은 파일에는 이 키가 들어가지 않아야 합니다.
키가 노출되면 새로 발급하고 Netlify 값을 바꾼 후 재배포해야 합니다.

선택 보안설정(필수 아님)
Key: DNM_INITIAL_LOGIN_ALLOWED_IPS
Value: 허용할 회사 외부 공인 IP의 쉼표 구분 목록
초기번호 로그인·최초 비밀번호 설정만 제한합니다. 일반 로그인 전체를 제한하는 설정은 아닙니다.
정확히 일치하는 IPv4/IPv6 주소만 지원하며 CIDR 표기는 지원하지 않습니다.
회사 Wi-Fi와 휴대폰 모바일망은 공인 IP가 다를 수 있습니다. 확인되지 않은 값을 임의 입력하지 마십시오.

[5. GitHub → Netlify 배포]
1) 패치 전체 병합 후 Commit → Push origin을 실행합니다.
2) 운영 전환 승인을 받은 코드를 main에 반영합니다.
3) 기존 Netlify 프로젝트에서 새 배포가 Published인지 확인합니다.
4) 배포 내용에 dnm-accounts 함수가 포함되었는지 확인합니다.
   계정 API 주소: /.netlify/functions/dnm-accounts
   이 주소를 주소창으로 열면 GET이므로 ‘POST 요청만 지원’이 나오는 것이 정상입니다.
5) Netlify 설정: Publish directory = public, Functions directory = netlify/functions
   제공 netlify.toml에 포함되어 있습니다. Build command는 기존처럼 비워둘 수 있습니다.
6) 서버 환경변수를 배포 이후 입력했다면 새 배포를 한 번 실행합니다.
7) 앱에서 Ctrl+Shift+R로 새로고침하고 기존 관리자 이메일/비밀번호로 로그인합니다.
8) 초기구축·운영 → 사용자 등록·초기화 → ‘계정 서버 연결 확인’을 누릅니다.

Netlify Drop으로 public 파일만 올리거나 PC에서 index.html만 열어서는 새 계정 서버기능이 실행되지 않습니다.
실제 HTTPS Netlify 주소에서 검사하십시오. 기존 로그인 연결 설정과 데이터는 유지합니다.

[6. 관리자가 직원 계정 등록]
1) 관리자 로그인 → 초기구축·운영 → 사용자 등록·초기화
   기준정보 → 작업자 화면의 ‘로그인 사용자 등록·초기화’ 버튼으로도 이동 가능합니다.
2) 성명·사번·부서·이메일로 작업자를 검색합니다.
3) 해당 작업자의 ‘로그인 사용자’ 체크를 선택합니다.
4) 로그인 ID에 직원 본인 이메일을 입력합니다.
   엑셀에 이메일이 없으면 추측하지 말고 직원에게 확인합니다.
5) ‘로그인 사용자로 등록’과 ‘실제 재직자 및 이메일 소유자를 확인’에 체크합니다.
6) 등록 사유를 확인하고 ‘계정 등록’을 누릅니다.
7) ‘첫 비밀번호 설정 대기’와 유효기한이 표시되는지 확인합니다.
8) 해당 직원에게만 DNM 접속주소, 본인 이메일, 초기번호 1111을 안내합니다.

동일 이메일의 기존 일반계정이 있으면 해당 계정을 연결하며 기존 역할·메뉴 권한을 유지합니다.
기존 관리자는 이 기능으로 초기화하지 않습니다. 이미 다른 작업자에게 연결된 이메일은 중복 연결하지 않습니다.
신규 계정만 담당자(member) + 본인 작업 조회/등록/수정과 본인 공유메모 조회 권한으로 시작합니다.
직원 전체 메일을 자동 추측하거나, 근로자 전원에게 무인 일괄계정 생성은 하지 않습니다.
이메일 연결 후 주소 수정은 이번 화면에서 지원하지 않습니다. 기존 연결을 임의로 해제하지 마십시오.
초기 설정은 이메일 확인메일을 보내는 방식이 아닙니다. 관리자 확인이 메일 소유 확인을 대신하므로 실제 본인 확인이 중요합니다.

[7. 직원의 첫 로그인]
1) DNM MES 주소를 PC 또는 휴대폰에서 엽니다.
2) 이메일: 관리자가 등록한 본인 이메일
3) 비밀번호 입력칸: 1111
4) 로그인 버튼을 누르면 ‘본인 비밀번호를 정해주세요’ 화면으로 이동합니다.
   이 단계에는 업무 화면과 업무 데이터가 제공되지 않습니다.
5) 새 비밀번호와 확인값을 입력합니다.
   문자 + 숫자 포함 12자 이상 / UTF-8 72바이트 이내
   영문 대·소문자, 숫자, 기호를 섞은 본인만 아는 비밀번호를 권장합니다.
   회사 Supabase의 비밀번호 정책이 더 엄격하면 그 기준도 충족해야 합니다.
6) ‘비밀번호 설정 완료’ 클릭
7) 로그인 화면으로 돌아오면 본인 이메일 + 새 비밀번호로 로그인합니다.
8) 이후에는 1111을 사용할 수 없습니다.

처음 번호는 발급 후 30분, 설정화면은 최대 5분입니다.
시간이 지났다면 관리자에게 초기화를 다시 요청하십시오. 기기 시계가 아니라 서버시간으로 확인합니다.
비밀번호는 관리자나 다른 직원에게 알려주지 않습니다.

[8. 비밀번호 분실·사용 중지·재사용]
- 분실: 관리자 → 사용자 등록·초기화 → 대상 직원의 ‘1111 초기화’
  변경 사유와 현재 관리자 본인의 비밀번호 입력 → 소유자 확인 → 초기화
  직원은 다시 1111로 접속하여 새 비밀번호를 설정합니다.
- 사용 중지: ‘로그인 사용자’ 체크 해제 → 사유·관리자 비밀번호·확인 → 사용 중지
  직원, Auth 계정, 과거 작업일보, 기존 메뉴 권한은 삭제하지 않습니다.
- 재사용: 사용 중지된 계정의 체크를 다시 선택하고 초기화 절차를 완료합니다.
- 본인/관리자 계정: 작업자 초기화 버튼으로 변경할 수 없으며 보호합니다.
- 본인 정상 변경: 로그인 후 위쪽 ‘비밀번호 변경’ → 현재 비밀번호 + 새 비밀번호 2회
  변경 후 다시 로그인합니다. 관리자가 새 비밀번호를 열람하는 기능은 없습니다.

초기화·사용 중지 시 이전 세션은 DB 접근규칙으로 차단하도록 구현했습니다.
열려 있던 화면에 이미 표시된 자료까지 원격으로 지우는 기능은 아닙니다.
오래된 화면은 새로고침·재로그인하고, 공용 PC는 사용 후 반드시 로그아웃합니다.

[9. 업무권한과 작업배정]
로그인 계정 발급과 생산작업 배정은 다릅니다.
사용자별 권한 · 전결에서 조회·등록·수정 및 본인/전체 범위를 지정합니다.
일반 작업자는 본인 작업 범위를 유지합니다. 조회만 필요한 직원에게 등록·수정 권한을 주지 마십시오.
현장 작업자는 기존 설비·작업자 연결 및 Routing 배포가 있어야 본인 작업 목록이 보입니다.
계정 생성·초기화는 제품·수주·Routing·작업일보를 새로 만들거나 삭제하지 않습니다.
관리자 역할은 전체 업무권한이므로 실제 승인된 담당자에게만 부여합니다.

[10. 오류별 대응]
‘Netlify 환경변수 설정 필요’ → 정확한 Key 이름 2개, 같은 프로젝트 URL/Secret key, Functions scope, 재배포 확인
‘PROJECT_MISMATCH’ → 서버 URL과 기존 config.js URL이 같은 프로젝트인지 확인
‘SQL 10 적용 확인’ → 10 적용 결과와 11 조회결과 확인. 이전 SQL 재실행 금지
‘계정 서버 응답 확인 불가’ → netlify/functions, server, netlify.toml까지 배포했는지 확인
‘현재 비밀번호 확인’ → 초기화 시 직원 비밀번호가 아니라 관리자 자신의 비밀번호 입력
‘초기 로그인 정보 확인 불가’ → 동일 이메일, 계정 설정 대기, 30분 유효기간, 사용중지 상태 확인
‘반복 요청 제한’ → 잠시 기다리고 관리자와 확인. 서버키·번호를 바꾸어 우회하지 않음
‘동일 작업자 처리 중’ → 2분 이후 목록 새로고침하여 상태 확인. 계속 클릭하지 않음
‘부분 생성’/‘초기화 재확인’ → 목록을 새로고침하고 같은 작업자에서 새 등록/초기화 요청. 기존 계정 삭제 금지
‘비밀번호 설정 불확실’ → 새 비밀번호로 한 번 확인. 차단되면 관리자 초기화 요청
‘사용할 작업 없음’ → 계정 오류와 구분. 업무권한·설비연결·Routing 배포 확인

[11. 반드시 실제 환경에서 검수]
A. 기존 관리자 로그인과 기존 수주·작업일보 건수 보존
B. 시험 작업자 1명 계정 등록 → 이메일/1111 → 개인 비밀번호 설정 → 새 비밀번호 로그인
C. 개인 비밀번호 설정 전 직접 API 조회·저장 및 메뉴 접근 차단
D. 작업자 A가 작업자 B의 담당자료나 관리자 기능에 접근하지 못하는지 확인
E. 기존 계정 재사용·중복 이메일·관리자/자기계정 초기화 금지 확인
F. 정상 비밀번호 변경 후 새 비밀번호 로그인, 이전 세션 및 갱신토큰의 업무 접근 차단
G. 관리자 초기화 → 과거 개인 비밀번호/세션의 업무 접근 차단 → 1111 설정 재개
H. 사용 중지 → 직원의 기존 토큰·재로그인으로 업무 자료 접근 차단, 작업이력은 보존
I. 30분/5분 만료, 잘못된 초기번호 반복 제한, 재사용 티켓 차단
J. 계정 서버 중단·환경변수 누락 상태에서 기존 정상 개인 로그인은 계속 작동하고 생성/초기화는 오류를 명확히 표시
K. 모바일·현장 PC에서 글자·숫자 입력, 메뉴·권한·작업 시작/종료 실제 검수

이 작성환경에서 실제 Supabase/Netlify에는 접속하지 않았습니다.
자동 검사와 모의 API 브라우저 검사는 수행했으나, 실제 PostgreSQL SQL 실행 및 Auth 관리자 API 동작은 미검증입니다.
반드시 GitHub Actions의 임시DB 검사와 별도 시험 Supabase의 위 검수를 통과한 후 운영에 적용하십시오.
기존 로그인 API 파일(public/api.js)과 config.js의 형식은 변경하지 않았습니다.
